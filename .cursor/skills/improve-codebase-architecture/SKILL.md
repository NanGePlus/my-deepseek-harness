# 改进代码库架构

揭示架构中的摩擦点，并提出**深化机会** —— 将浅层模块重构为深层模块的重构方案。目标是提高可测试性和 AI 可导航性。

## 术语表

在每个建议中精确使用这些术语。保持语言一致是关键 —— 不要偏离到“组件”、“服务”、“API”或“边界”等词。完整定义见 [LANGUAGE.md](LANGUAGE.md)。

- **模块（Module）** —— 任何拥有接口和实现的东西（函数、类、包、切片）。
- **接口（Interface）** —— 调用者使用该模块所需知道的一切：类型、不变量、错误模式、顺序、配置。不仅仅是类型签名。
- **实现（Implementation）** —— 内部的代码。
- **深度（Depth）** —— 接口处的杠杆效应：一个小接口背后承载了大量行为。**深** = 高杠杆。**浅** = 接口的复杂度几乎与实现相当。
- **接缝（Seam）** —— 接口所在的位置；无需原地编辑即可改变行为的地方。（使用这个词，而不是“边界”。）
- **适配器（Adapter）** —— 在接缝处满足某个接口的具体实现。
- **杠杆（Leverage）** —— 调用者从深度中获得的好处。
- **局部性（Locality）** —— 维护者从深度中获得的好处：变更、bug、知识都集中在一个地方。

关键原则（完整列表见 [LANGUAGE.md](LANGUAGE.md)）：

- **删除测试**：想象删除这个模块。如果复杂性消失了，那它之前只是一个透传。如果复杂性在 N 个调用者中重新出现，那这个模块之前是值得保留的。
- **接口就是测试面。**
- **一个适配器 = 假设性的接缝。两个适配器 = 真正的接缝。**

本 skill 受项目的领域模型启发。领域语言为良好的接缝提供了命名；ADR 记录了本 skill 不应重复争论的决策。

## 流程

### 1. 探索

首先阅读项目的领域术语表以及你所涉及领域内的任何 ADR。

若 `spec-driven` 或 `mockup-driven`，还需检查：

- UI 代码中是否存在绕过 `docs/design/DESIGN.md` Token 语义的硬编码颜色字面量
- 各 platform-id 是否仍共享 DESIGN.md 品牌 Token 语义（见 `platforms.md` 平台清单）
- UI 代码是否遵循 `docs/design/platforms.md` 中对应 platform-id 的组件映射

然后使用 `subagent_type=Explore` 的 Agent 工具来遍历代码库。不要遵循僵化的启发式规则 —— 有机地探索，并记录下你感受到摩擦的地方：

- 理解一个概念需要在许多小模块之间来回跳转的地方在哪里？
- 哪些模块是**浅层**的 —— 接口的复杂度几乎与实现相当？
- 哪些地方仅仅为了可测试性而提取了纯函数，但真正的 bug 却隐藏在它们是如何被调用的逻辑中（没有**局部性**）？
- 哪些地方紧密耦合的模块会跨过它们的接缝发生泄漏？
- 代码库的哪些部分未经测试，或者难以通过其当前接口进行测试？

对你怀疑是浅层的任何东西应用**删除测试**：删除它会集中复杂性，还是仅仅移动了复杂性？“是的，会集中”是你想要的信号。

### 2. 将候选建议以 HTML 报告形式呈现

将一个自包含的 HTML 文件写入操作系统临时目录，这样就不会在仓库中留下任何文件。从 `$TMPDIR` 环境变量解析临时目录，回退到 `/tmp`（Windows 上回退到 `%TEMP%`），并写入 `<tmpdir>/architecture-review-<timestamp>.html`，这样每次运行都会生成一个新文件。使用以下命令为用户打开该文件：Linux 上用 `xdg-open <path>`，macOS 上用 `open <path>`，Windows 上用 `start <path>`，并告知用户该文件的绝对路径。

报告通过 **CDN 引入 Tailwind** 进行布局和样式设计，并通过 **CDN 引入 Mermaid** 来绘制能够可靠传达结构的图表（如关系图、流程图、序列图）。将 Mermaid 与手工编写的 CSS/SVG 视觉元素结合使用 —— 当关系呈现为图结构时（调用图、依赖关系、序列）使用 Mermaid，当需要更具说明性的内容时（例如块状图、剖面图、折叠动画）则使用手写的 div/SVG。每个候选建议都应有**前后对比的可视化呈现**。要注重视觉化表达。

对于每个候选建议，使用与之前相同的模板，但以卡片形式呈现：

- **涉及文件** —— 涉及哪些文件/模块
- **问题** —— 当前架构为什么引起摩擦
- **解决方案** —— 用通俗语言描述会发生什么变化
- **收益** —— 用局部性和杠杆效应来解释，以及测试将如何改进
- **前后对比图** —— 并排展示，自定义绘制，说明浅层问题以及如何深化
- **推荐强度** —— 从 `Strong`（强烈推荐）、`Worth exploring`（值得探索）、`Speculative`（待验证）中选一个，以徽章形式呈现

报告以**首选推荐**章节结尾：你会先处理哪个候选建议，以及为什么。

**领域概念使用 `CONTEXT.md` 中的词汇，架构概念使用 [LANGUAGE.md](LANGUAGE.md) 中的词汇。**

**ADR 冲突**：如果某个候选建议与现有的 ADR 相矛盾，只有当摩擦确实大到值得重新讨论该 ADR 时，才将其提出来。在卡片中明确标记（例如警告框：_“与 ADR-0007 冲突 — 但值得重新讨论，因为……”_）。不要列出 ADR 所禁止的每一个理论上的重构。

完整的 HTML 框架、图表模式及样式指南请参见 [HTML-REPORT.md](HTML-REPORT.md)。

暂时不要提出具体的接口设计。文件生成后，请询问用户：“您希望探索其中的哪一个？”

### 3. 拷问式对话循环

一旦用户选择了某个候选建议，就进入拷问式对话。与用户一起遍历设计树 —— 约束条件、依赖关系、深化后模块的形态、接缝背后是什么、哪些测试能够保留下来。

当决策固化时，副作用会内联发生：

- **用一个 `CONTEXT.md` 中不存在的概念来命名一个深化后的模块？** 将该术语添加到 `CONTEXT.md` 中 —— 遵循与 `/grill-with-docs` 相同的规定。如果文件不存在，则惰性创建。
- **在对话中精炼了一个模糊的术语？** 立即更新 `CONTEXT.md`。
- **用户出于一个关键性原因拒绝了该候选建议？** 提供一个 ADR，措辞如下：“_需要我将此记录为一个 ADR，以便未来的架构评审不会再次提出这个建议吗？_” 仅当未来的探索者确实需要这个理由来避免再次提出同样的建议时才提供 —— 跳过短暂性的理由（如“现在不值得做”）和不言自明的理由。格式参见 [ADR-FORMAT.md](../grill-with-docs/ADR-FORMAT.md)。
- **想要探索深化后模块的备选接口？** 参见 [INTERFACE-DESIGN.md](INTERFACE-DESIGN.md)。
