# 接口设计

当用户想要为某个选定的深化候选方案探索备选接口时，使用这种并行的子 Agent 模式。基于“设计两次”原则 —— 你的第一个想法不太可能是最好的。

使用 [LANGUAGE.md](LANGUAGE.md) 术语——**模块（Module）**、**接口（Interface）**、**接缝（Seam）**、**适配器（Adapter）**、**杠杆（Leverage）**。

## 流程

### 1. 界定问题空间

在启动子 Agent 之前，针对所选定的候选方案，编写一个面向用户的问题空间说明：

- 任何新接口都需要满足的约束条件
- 它将依赖的依赖项，以及这些依赖项属于哪个类别（参见 [DEEPENING.md](DEEPENING.md)）
- 一个粗略的示例代码草图，用于将约束条件具体化 —— 不是提案，只是让约束条件更具体的一种方式

将此内容展示给用户，然后立即进入第二步。在子 Agent 并行工作的同时，用户可以阅读和思考。

### 2. 启动子 Agent

使用 Agent 工具并行启动至少 3 个子 Agent。每个子 Agent 必须为该深化后的模块产出一个**截然不同**的接口。

使用各自独立的技术简报（包含文件路径、耦合细节、来自 [DEEPENING.md](DEEPENING.md) 的依赖类别、接缝背后是什么）来提示每个子 Agent。该简报与第一步中面向用户的问题空间说明是相互独立的。为每个 Agent 分配一个不同的设计约束：

- Agent 1：“最小化接口 —— 最多追求 1-3 个入口点。最大化每个入口点的杠杆效应。”
- Agent 2：“最大化灵活性 —— 支持许多用例和扩展。”
- Agent 3：“为最常见的调用者进行优化 —— 让默认情况变得简单。”
- Agent 4（如果适用）：“围绕端口与适配器进行设计，以处理跨接缝的依赖关系。”

在简报中同时包含 [LANGUAGE.md](LANGUAGE.md) 的词汇和 `CONTEXT.md` 的词汇，以便每个子 Agent 在命名时能与架构语言和项目的领域语言保持一致。

每个子 Agent 输出：

1. 接口（类型、方法、参数 —— 以及不变量、顺序、错误模式）
2. 使用示例，展示调用者如何使用它
3. 实现隐藏在接缝背后的内容
4. 依赖策略和适配器（参见 [DEEPENING.md](DEEPENING.md)）
5. 权衡 —— 哪些地方杠杆效应高，哪些地方薄弱

### 3. 展示与比较

依次展示各个设计方案，以便用户能够吸收每个方案的内容，然后用文字进行比较。通过**深度**（接口处的杠杆效应）、**局部性**（变更集中的地方）和**接缝位置**来进行对比。

比较之后，给出你自己的推荐：你认为哪个设计最优秀，以及为什么。如果不同设计中的元素可以很好地组合在一起，则提出一个混合方案。要有主见 —— 用户需要的是一个强有力的判断，而不是一个待选菜单。
