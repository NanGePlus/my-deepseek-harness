# 深化

在给定依赖关系的情况下，如何安全地深化一组浅层模块。假设使用 [LANGUAGE.md](LANGUAGE.md) 中的词汇 —— **模块**、**接口**、**接缝**、**适配器**。

## 依赖类别

在评估一个待深化的候选方案时，对其依赖项进行分类。依赖类别决定了深化后的模块如何跨接缝进行测试。

### 1. 进程内依赖

纯计算、内存状态、无 I/O。总是可以深化 —— 合并模块，直接通过新接口进行测试。不需要适配器。

### 2. 本地可替换依赖

具有本地测试替代品的依赖项（例如用于 Postgres 的 PGLite、内存文件系统）。如果存在这样的替代品，则可以深化。深化后的模块在测试时，会在测试套件中运行该替代品。接缝是内部的；模块的外部接口处无需端口。

### 3. 远程但归己所有（端口与适配器）

跨网络边界的自有服务（微服务、内部 API）。在接缝处定义一个**端口**（接口）。深层模块拥有逻辑；传输层作为**适配器**注入。测试使用内存中的适配器。生产环境使用 HTTP/gRPC/队列适配器。

建议表述示例：*“在接缝处定义一个端口，为生产环境实现一个 HTTP 适配器，为测试实现一个内存适配器，这样即使逻辑是跨网络部署的，它也能位于一个深层模块中。”*

### 4. 真正的外部依赖（Mock）

你无法控制的第三方服务（如 Stripe、Twilio 等）。深化后的模块将外部依赖作为注入的端口接收；测试提供 mock 适配器。

## 接缝规范

- **一个适配器意味着一个假设性的接缝。两个适配器意味着一个真正的接缝。** 除非至少有（通常是生产环境和测试环境）两个适配器是合理的，否则不要引入端口。只有一个适配器的接缝只是间接层。
- **内部接缝与外部接缝。** 一个深层模块可以有内部接缝（私有于其实现，供其自身测试使用）以及其接口处的外部接缝。不要仅仅因为测试使用了内部接缝，就把它们暴露在外部接口中。

## 测试策略：替换，而不是叠加

- 一旦在深化后模块的接口处存在测试，原来那些针对浅层模块的单元测试就变成了冗余 —— 删除它们。
- 在深化后模块的接口处编写新的测试。**接口就是测试面**。
- 测试通过接口断言可观察的结果，而不是内部状态。
- 测试应该能在内部重构后存活下来 —— 它们描述的是行为，而不是实现。如果一个测试在实现改变时必须跟着改变，那它就是在测试超越接口的内容。
