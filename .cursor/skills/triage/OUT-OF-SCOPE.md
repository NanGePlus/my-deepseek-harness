# 范围外知识库

仓库中的 `.out-of-scope/` 目录存储了被拒绝的功能请求的持久化记录。它有两个目的：

1. **机构记忆** —— 某个功能为什么被拒绝，这样当 issue 关闭时，推理过程不会丢失
2. **去重** —— 当新 issue 与之前被拒绝的请求匹配时，技能可以呈现之前的决策，而不是重新争论一遍

## 目录结构

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

每个**概念**一个文件，而不是每个 issue 一个文件。请求同一事物的多个 issue 被归并在一个文件下。

## 文件格式

文件应以轻松、可读的风格编写 —— 更像是一个简短的文档，而不是数据库条目。使用段落、代码示例和示例来使推理清晰，并对第一次接触它的人有帮助。

```markdown
# 深色模式

本项目不支持深色模式或面向用户的主题切换。

## 为什么这属于范围外

渲染管道假定使用在 `ThemeConfig` 中定义的单一颜色调色板。支持多个主题将需要：

- 一个包裹整个组件树的主题上下文提供者
- 每个组件的主题感知样式解析
- 用于存储用户主题偏好设置的持久化层

这是一个重大的架构变更，与项目专注于内容创作的定位不符。主题化是下游使用者的关注点，他们可以嵌入或重新分发输出。

```ts
// 当前的 ThemeConfig 接口并非为运行时切换而设计：
interface ThemeConfig {
  colors: ColorPalette; // 单一调色板，在构建时解析
  fonts: FontStack;
}
```

## 历史请求

- #42 —— “添加深色模式支持”
- #87 —— “为无障碍改进提供夜间主题”
- #134 —— “深色主题选项”
```

### 文件命名

为概念使用简短、描述性的小写短横线命名（kebab-case）：`dark-mode.md`、`plugin-system.md`、`graphql-api.md`。名称应具有足够的可识别性，使浏览目录的人无需打开文件就能理解被拒绝的是什么。

### 编写理由

理由应该是实质性的 —— 不是“我们不想要这个”，而是为什么。好的理由可以引用：

- 项目范围或理念（“本项目专注于 X；主题化是下游使用者的关注点”）
- 技术约束（“支持这将需要 Y，这与我们的 Z 架构相冲突”）
- 战略决策（“我们选择使用 A 而不是 B，因为……”）

理由应该是持久的。避免引用临时情况（“我们现在太忙了”）—— 那些不是真正的拒绝，而是推迟。

## 何时检查 `.out-of-scope/`

在分拣期间（步骤 1：收集上下文），读取 `.out-of-scope/` 中的所有文件。在评估新 issue 时：

- 检查该请求是否匹配一个现有的范围外概念
- 匹配依据的是概念相似性，而不是关键词 —— “夜间主题”会匹配 `dark-mode.md`
- 如果存在匹配项，则向维护者呈现：“这与 `.out-of-scope/dark-mode.md` 相似 —— 我们之前因为 [理由] 拒绝了它。你仍然持相同看法吗？”

维护者可以：

- **确认** —— 新 issue 被添加到现有文件的“Prior requests”列表中，然后关闭
- **重新考虑** —— 删除或更新范围外文件，然后 issue 继续正常的分拣流程
- **不同意** —— 这些 issue 相关但不同，继续进行正常分拣

## 何时写入 `.out-of-scope/`

仅当一个**enhancement**（而不是 bug）被裁定为 `wontfix` 时。流程如下：

1. 维护者决定一个功能请求属于范围外
2. 检查是否已存在匹配的 `.out-of-scope/` 文件
3. 如果是：将新 issue 追加到“Prior requests”列表
4. 如果否：创建新文件，包含概念名称、决策、理由和第一个历史请求
5. 在 issue 上发布评论，解释决策并提及该 `.out-of-scope/` 文件
6. 使用 `wontfix` 标签关闭 issue

## 更新或删除范围外文件

如果维护者改变了对某个先前被拒绝的概念的看法：

- 删除该 `.out-of-scope/` 文件
- 技能不需要重新打开旧 issue  —— 它们是历史记录
- 触发重新考虑的新 issue 将进行正常的分拣流程
