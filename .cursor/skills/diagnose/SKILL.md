# 诊断

一套用于排查疑难 bug 的方法论。只有在明确有正当理由时，才能跳过某个阶段。

在探索代码库时，使用项目的领域术语表来建立相关模块的清晰心智模型，并检查你所涉及领域内的 ADR。

## 第一阶段 —— 建立反馈回路

**这就是本 skill 的核心所在。** 其他的一切都只是机械操作。如果你能针对这个 bug 建立一个快速、确定性、可由 Agent 运行的通过/失败信号，你就一定能找到原因 —— 无论是通过二分法、假设检验还是注入观测，都依赖于这个信号。如果没有这个信号，盯着代码看再久也救不了你。

在这个阶段要投入不成比例的努力。**要激进。要有创造力。拒绝放弃。**

### 构建反馈回路的方法 —— 大致按此顺序尝试

1. **失败的测试** —— 在能够触达 bug 的某个接缝处编写单元测试、集成测试或端到端测试。
2. **Curl / HTTP 脚本** —— 针对正在运行的开发服务器执行。
3. **CLI 调用** —— 使用固定输入，对标准输出与已知良好的快照进行 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）—— 驱动 UI，断言 DOM / 控制台 / 网络。
5. **回放捕获的 trace** —— 将真实的网络请求 / payload / 事件日志保存到磁盘；在隔离环境中通过代码路径回放。
6. **临时测试工具** —— 启动系统的一个最小子集（单个服务，依赖项用 mock），通过单个函数调用执行触发 bug 的代码路径。
7. **属性 / 模糊测试循环** —— 如果 bug 是“有时输出错误”，运行 1000 个随机输入，寻找失败模式。
8. **二分法测试工具** —— 如果 bug 出现在两个已知状态（commit、数据集、版本）之间，自动化“在状态 X 启动、检查、重复”的过程，以便使用 `git bisect run`。
9. **差分循环** —— 在旧版本 vs 新版本（或两种配置）上运行相同的输入，对输出进行 diff。
10. **有人参与的（HITL）bash 脚本** —— 最后的手段。如果必须由人点击，使用本 Skill 目录下的 `scripts/hitl-loop.template.sh` 来驱动人工操作，使循环仍然保持结构化。捕获的输出会反馈给你。

构建出正确的反馈回路，bug 就修复了 90%。

### 对反馈回路本身进行迭代

把反馈回路当作一个产品来对待。一旦你有了一个**可运行的回路**，就问自己：

- 我能让它更快吗？（缓存设置、跳过不相关的初始化、缩小测试范围。）
- 我能让信号更精确吗？（针对具体的症状进行断言，而不是“没崩溃”。）
- 我能让它更确定吗？（固定时间、固定随机数种子、隔离文件系统、冻结网络。）

一个 30 秒且不稳定的回路，比没有回路好不到哪去。一个 2 秒且确定性的回路，是调试的超能力。

### 非确定性 bug

目标不是干净复现，而是**提高复现率**。循环触发 100 次、并行、加压、缩小时间窗口、注入 sleep。50% 偶发的 bug 可调试；1% 不行——持续提高复现率直到可调试。

### 当你确实无法构建反馈回路时

停下来，明确地说明这一点。列出你尝试过的方法。向用户请求：（a）能够复现该问题的环境访问权限，（b）捕获到的产物（HAR 文件、日志转储、核心转储、带时间戳的屏幕录制），或（c）添加临时生产环境探针的权限。**不要**在没有反馈回路的情况下推进到假设阶段。

在拥有一个你确信可靠的反馈回路之前，不要进入第二阶段。

## 第二阶段 —— 复现

运行反馈回路。观察 bug 出现。

确认：

- [ ] 回路产生的是**用户**所描述的那种失败模式 —— 而不是恰好邻近的其他失败。搞错 bug 就会搞错修复。
- [ ] 该失败在多次运行中是可复现的（对于非确定性 bug，其复现率要足够高，以便进行调试）。
- [ ] 你已经捕获了确切的症状（错误信息、错误的输出、缓慢的耗时），以便后续阶段能够验证修复是否真正解决了问题。

在复现 bug 之前，不要继续推进。

## 第三阶段 —— 提出假设

在测试任何一个假设之前，生成 **3-5 个排好优先级的假设**。只生成一个假设会让你固着于第一个看似合理的想法上。

每个假设必须是**可证伪的**：陈述它所做出的预测。

> 格式：“如果 <X> 是原因，那么 <改变 Y> 会使 bug 消失 / <改变 Z> 会使它更糟。”

如果你无法陈述出预测，那么这个假设只是一种感觉 —— 要么将其打磨清晰，要么丢弃它。

**在测试之前，将排好序的假设列表展示给用户。** 他们通常拥有领域知识，能立刻重新排序（例如“我们刚刚对 #3 对应的模块部署了一个变更”），或者知道他们自己已经排除过哪些假设。这是一个低成本、省时间的检查点。如果用户不在，可以按照你的排序继续推进。

## 第四阶段 —— 注入观测（探针）

每个探针必须对应第三阶段中的一个具体预测。**一次只改变一个变量。**

工具偏好：

1. **调试器 / REPL 交互式检查** —— 如果环境支持的话。一个断点胜过十条日志。
2. **针对性日志** — 在能区分各个假设的边界处添加针对性日志。
3. 永远不要「全量日志再 grep」。

**为每条调试日志打上唯一的前缀标签**，例如 `[DEBUG-a4f2]`。最后的清理工作只需要一次 grep 即可完成。未加标签的日志会保留；加标签的日志会被清除。

**针对性能分支。** 对于性能回归问题，日志通常是不可靠的。取而代之的做法是：建立一个基线测量（耗时测试工具、`performance.now()`、性能分析器、查询计划），然后进行二分定位。先测量，后修复。

## 第五阶段 —— 修复 + 回归测试

**在修复之前**编写回归测试 —— 但前提是存在**合适的测试接缝**。

一个合适的测试接缝是指：在这个接缝上编写的测试，能够真实地模拟出 bug 在**调用点**发生的实际模式。如果唯一可用的接缝太浅（例如 bug 需要多个调用者才能触发，却只能写一个单一调用者的测试；或者单元测试无法复现触发 bug 的那条调用链），那么在这个接缝上编写的回归测试只会带来虚假的信心。

**如果不存在合适的接缝，这本身就是一项发现。** 将其记录下来。代码库的架构正在阻碍 bug 被锁定。将此标记给下一阶段。

如果存在合适的接缝：

1. 将最小化的复现步骤转换为该接缝上的一个失败测试。
2. 观察它失败。
3. 应用修复。
4. 观察它通过。
5. 针对原始的（未最小化的）场景重新运行第一阶段的反馈回路。

## 第六阶段 —— 清理 + 事后总结

在宣布完成之前必须完成：

- [ ] 原始的复现步骤不再能复现 bug（重新运行第一阶段的反馈回路）
- [ ] 回归测试通过（或者已经记录下缺少合适接缝的情况）
- [ ] 所有 `[DEBUG-...]` 探针代码已被移除（用前缀进行 grep 确认）
- [ ] 临时原型已被删除（或移到了一个明确标记的调试位置）
- [ ] 最终被证实正确的假设已记录在 commit / PR 消息中 —— 以便下一个调试者学习

**然后问：什么本可以阻止这个 bug 发生？** 如果答案涉及架构变更（没有好的测试接缝、调用者纠缠不清、隐藏的耦合），请将具体细节交接给 `/improve-codebase-architecture` skill。**在修复完成之后**再提出建议，而不是在之前 —— 你现在拥有的信息比你开始时要多。
