## 领域感知

探索代码库时，同时查找现有文档：

### 文件结构

```
/
├── CONTEXT.md
├── docs/
│   ├── adr/
│   │   ├── 0001-event-sourced-orders.md
│   │   └── 0002-postgres-for-write-model.md
│   └── design/
│       └── DESIGN.md
└── src/
```

惰性创建文件——仅有内容可写时才创建。若无 `CONTEXT.md`，在首个术语确定时创建。若无 `docs/adr/`，在需要首个 ADR 时创建。若无 `docs/design/DESIGN.md`，在 UI 模式与品牌视觉规范确认后创建。

## 会话期间

### 默认拷问顺序（必须遵循）

除非用户明确要求偏离，按此顺序进行：

1. **领域规格拷问优先** — 稳定业务术语、边界、状态与策略语义。
2. **技术规格拷问其次** — 锁定架构/工具/运维基线，记录值得 ADR 的决策。
3. **UI 模式拷问最后** — 选定 UI 编码模式；模式 2/3 时确认品牌视觉设计规范并写入 `DESIGN.md`。

不要过早跳到后续阶段。若问题混合多层，拆分并将各答案路由到对应阶段与文档目标。

### 对照词汇表挑战

当用户使用的术语与 `CONTEXT.md` 现有语言冲突时，立即指出。「你的词汇表将『取消』定义为 X，但你似乎指 Y——到底是哪个？」

### 厘清模糊语言

当用户使用模糊或多义术语时，提出精确的规范术语。「你说『账户』——是指 Customer 还是 User？这是两回事。」

### 讨论具体场景

讨论领域关系时，用具体场景做压力测试。发明探测边界情况、迫使用户精确概念边界的场景。

### 与代码交叉核对

当用户陈述某物如何工作时，检查代码是否一致。若发现矛盾，指出：「你的代码取消的是所有订单，但你刚说可以部分取消——哪个对？」

### 内联更新 CONTEXT.md

术语确定时，当场更新 `CONTEXT.md`。不要批量——发生时即捕获。格式见 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md)。

`CONTEXT.md` 应完全不含实现细节。不要把它当规格、草稿本或实现决策仓库。它只是词汇表，仅此而已。

### 规格边界与文档路由（必须执行）

必须区分三类决策，并写入正确位置：

1. **领域规格（业务语言与规则）** → `CONTEXT.md`
2. **技术规格（架构与技术栈锁定）** → `docs/adr/*.md`
3. **UI 规格（品牌视觉设计规范）** → `docs/design/DESIGN.md`

#### 路由规则

- 仅当决策关于领域含义、业务状态、角色边界或策略语义时，写入 `CONTEXT.md`。
- 当决策是架构/工具/部署/认证/数据/可观测性且难以逆转或涉及权衡时，写入 `docs/adr/`。
- 当决策关于创意方向、色彩、字体、层级、组件形态或视觉宜忌时，写入 `docs/design/DESIGN.md`。
- **功能页面规格**（页面布局、业务字段排列、功能专属复合组件）**不属于** `DESIGN.md`：mockup-driven 由 PNG 稿承载；spec-driven 在实现规划阶段处理，不写入设计系统文档。

#### 硬性禁止

- 永远不要将框架选择、部署拓扑、CI 工具或运行时基础设施细节写入 `CONTEXT.md`。
- 永远不要将视觉规格（颜色/字体/组件语义）写入 `CONTEXT.md`。
- 不要用 ADR 存储品牌视觉规范；UI 视觉决策属于 `docs/design/DESIGN.md`。
- 永远不要在 `DESIGN.md` 写页面名、业务字段布局、功能专属复合组件、领域术语或业务状态名。

#### 歧义处理

若决策看似混合（领域 + 技术 + UI），拆成独立的一问一答，分别路由输出，而非在一个文件中记录混合陈述。

#### 写入前自检（3 行，强制）

写入任何决策前，快速检查：

1. 这是关于业务含义/规则吗？ → 写入 `CONTEXT.md`
2. 这是难以逆转的技术/架构选择吗？ → 写入 `docs/adr/*.md`
3. 这是品牌视觉/交互语义指导吗？ → 写入 `docs/design/DESIGN.md`

### 谨慎提供 ADR

仅当以下三者均为真时才提议创建 ADR：

1. **难以逆转** — 日后改主意成本可观
2. **无上下文时令人意外** — 未来读者会纳闷「为何这样做？」
3. **真实权衡的结果** — 有真正备选且因具体理由选了其一

若三者缺一，跳过 ADR。格式见 [ADR-FORMAT.md](./ADR-FORMAT.md)。

### 技术栈拷问（领域之后、UI 之前，架构基线未固定时）

若用户未明确固定项目级技术栈，**不要**直接跳到设计文档或实现文件创建。领域术语稳定后，启动专属技术栈拷问分支，一次一问并给出推荐选项。

以下任一为真时触发此分支：
- 用户说技术栈未定 / 未最终确定
- 现有仓库内未定义后端/前端/数据/部署基线
- 团队工作流已定，但执行工具/框架选择仍开放

按此顺序（逐一询问，每次等待回答）：
1. 语言策略：全栈统一 vs 多语言
2. 后端框架与 API 风格基线
3. 数据库 + ORM/迁移纪律
4. 缓存/队列/调度器基线
5. Web 端框架 + 组件库
6. 移动应用技术路线 + 组件库（如 APP、H5、微信小程序）
7. 多包管理/多项目协作方案（如 Monorepo、Polyrepo、包管理器、任务编排工具等，推荐 Monorepo）
8. 认证/会话模型
9. 契约/文档机制（如 OpenAPI）
10. 测试基线（单元/集成/冒烟/手工）
11. 质量与 CI 门禁
12. 环境/配置/密钥管理
13. 可观测性/日志/指标基线
14. 部署形态（模块化单体 vs 微服务）

技术栈决策成型时：
- 架构/工具锁定决策**必须**写为 ADR；其他决策可按 ADR 标准选择是否写入
- 保持 `CONTEXT.md` 以词汇表为先；避免变成完整技术规格
- 仅在技术栈基线明确确认后，才进入 `docs/design/` 与实现规划

技术栈分支收尾规则：
- 用最终确认问题锁定技术栈基线
- 确认后，提议创建/追加 ADR，然后进入 UI 模式拷问（若计划含 UI）

### UI 模式的拷问（领域 + 技术基线清晰后）

当计划可能包含 UI 时，仅在领域术语与技术栈基线确认后启动。一次一问，每问给出推荐答案，等待反馈后再继续。

#### 第一步：选定 UI 编码模式

一次只问一题，用决策树引导用户明确三选一：

```
有没有可视化页面？
├─ 否 → 模式 1 headless（无可视化 UI）
└─ 是 → 会不会提供 UI 设计稿 PNG？
    ├─ 否 → 模式 2 spec-driven（规范驱动 UI）
    └─ 是 → 模式 3 mockup-driven（稿驱动 UI；全部 UI 页须提供 PNG，非部分页面）
```

| 模式 | 后续 |
|------|------|
| 1 headless（无可视化 UI） | UI 拷问结束，不创建 `docs/design/` |
| 2 spec-driven（规范驱动 UI） | 继续品牌视觉拷问 |
| 3 mockup-driven（稿驱动 UI） | 继续品牌视觉拷问 |

- **模式 1 headless（无可视化 UI）** — 无可视化页面（纯 API/CLI/库）。
- **模式 2 spec-driven（规范驱动 UI）** — 有页面，**永不**提供 PNG 设计稿。
- **模式 3 mockup-driven（稿驱动 UI）** — 有页面，**全部** UI 页须提供 PNG 设计稿。

若仓库已有 `docs/design/DESIGN.md`，先读其中已记录的 UI 模式；与用户确认是否沿用或覆盖。

#### 第二步：品牌视觉设计规范（仅模式 2 spec-driven / 模式 3 mockup-driven）

目标：定出可还原**品牌板**（色板四组色阶 + 三档字体样张 + 关键组件样张）的叙事性设计规范。一次只问一题，每问给出推荐答案，等待反馈后再继续。

**技术栈 → UI 桥接（Agent 自查，不必多问用户）：** 品牌视觉拷问期间，读 `docs/adr/` 与技术栈拷问结论，识别受限运行时（微信小程序、React Native、Flutter、原生 APP 等）。触及时，相关轮次须覆盖 **实现约束**，不得只写稿面规格：

| 桥接场景 | 触发轮次 | 须覆盖 |
|---------|---------|--------|
| 小程序 / RN / Flutter / 原生 APP | 第 3 轮字体 | 自定义字体加载策略、fallback 栈、稿面字体 vs 实现字体 |
| mockup-driven（任意运行时） | 第 3 轮字体、第 4 轮叠色、写入步骤 | PNG 管视觉；DESIGN 管 Token 与实现边界 |

按此顺序逐一拷问：

1. **创意北极星** — 设计哲学与创意代号；产品气质；如何打破模板感（留白、不对称、层叠等）
2. **色彩与表面** — 分两步拷问，仍一次一问：
   - **2a 品牌四色板** — Primary / Secondary / Tertiary / Neutral 主色与各 8–10 阶色阶；表面层级（base → card → modal）；布局边界规则（如禁止实线边框、用什么替代）
   - **2b 语义色** — error / success / warning / info 是否从品牌色衍生还是独立色；各给 Token + HEX（不适用项与用户确认跳过并记录）。**只定义跨产品通用的语义色**，不读 `CONTEXT.md`，不写业务状态名或状态色映射表
3. **字体** — **前置探测（Agent 自查，不必多问用户）：** 若 ADR / 技术栈含微信小程序、React Native、Flutter、原生 APP 等受限运行时，本轮回须覆盖 **加载策略 / fallback 栈 / 稿面 vs 实现**（可合并为一问）。仍一次一问：
   - 字体族配对 — Headline / Body / Label；字号阶梯与层级对比策略
   - 实现约束（受限运行时触发，或 mockup-driven 下稿面字体与实现字体不一致时）— 自定义字体能否加载？不能时的 fallback 栈；**稿面字体**（PNG / 品牌板样张用）与 **实现字体**（代码 fallback 用）是否相同；mockup-driven 下 PNG 管视觉，DESIGN 须写明实现边界，避免交付争议
4. **层级与深度** — 色调叠层原则；阴影规格；必要时 ghost border 规则；**收尾：叠色固化拷问**（可合并为一问）—— 盘点组件/状态中拟复用的叠色（如 `primary @ 3%` / `@ 8%` / `@ 10%` / `@ 15%`），凡 **≥2 次复用** 者须输出 **叠色对照表**（Token 名 + 基准色 + 不透明度 + 预计算 HEX）；仅出现 1 次且不再复用的叠色可暂不进入对照表，但 §5 须直接写 HEX 或引用已有 Token
5. **通用 UI 原语** — 与 [DESIGN-TEMPLATE.md](./DESIGN-TEMPLATE.md) 品牌板组件表逐字对齐，仍一次一问，按序逐项拷问。**只写与业务无关的可复用 atom/molecule**，每项覆盖默认 / 悬停 / 禁用 / 选中（若适用）态与 Token：

   **§5 硬性边界（Agent 自检，触界则改写或移除）：**
   - ✅ 允许：按钮变体、输入框态、卡片容器样式、列表行样式、导航形态、搜索框形态、徽章组件形态、图标按钮、空状态 pattern、Loading pattern
   - ❌ 禁止：页面名、业务字段布局、功能专属复合组件、领域术语、业务状态名
   - 功能页面与业务组件：mockup-driven → PNG 稿；spec-driven → 实现规划阶段，**不写入 DESIGN.md**

   按序拷问：
   1. 按钮变体 — 主 / 次 / 描边 / 文字 / **反色**（深色底或深色面上的浅色按钮）
   2. 输入与表单 — 默认 / 聚焦 / 错误态（错误态引用 §2 `semantic-error` Token，禁止临时 HEX）
   3. 卡片容器 — 圆角、内边距、阴影、背景 Token；**不写**业务内容排列
   4. 列表行 — 行高、行间距、分隔方式、选中 / 高亮态视觉规则；**不写**业务列字段
   5. 导航 — 顶栏 / 侧栏 / 底栏 Tab 等主形态与选中态
   6. 搜索框 — 输入框与下拉结果的**视觉** pattern（若无全局搜索，与用户确认跳过并记录）；**不写**业务占位符
   7. 状态徽章 — 组件形态（padding、圆角、字号）；附 1 条通用样例（如引用 `semantic-error`），**不写**业务状态名或状态色映射
   8. 图标按钮 — 尺寸、描边粗细、默认 / 悬停 / 选中态 Token（底栏 Tab 图标选中态须在此明确）
   9. 空状态 — 插画或图标尺寸、文案字号、可选 CTA 按钮变体（通用 pattern，不写具体业务文案）
   10. Loading — spinner / 骨架屏形态与尺寸（若产品无异步等待场景，与用户确认跳过并记录）
6. **宜忌** — 3–5 条 Do 与 3–5 条 Don't，约束常见返工点；宜忌中提到的视觉模式（如空状态）须在 §5 已有对应组件规格，禁止只写在宜忌而不写组件

#### 第三步：确认并惰性写入

用户确认品牌视觉规范后，惰性创建或更新 `docs/design/DESIGN.md`。

**模板合规（强制）：** 输出须**严格按照** [DESIGN-TEMPLATE.md](./DESIGN-TEMPLATE.md) 中「模板」章节的 Markdown 结构生成——**不得**自行增删章节、调换顺序、合并子节或改用其他提纲。写入前须完整读取该模板；写入后须逐节对照模板验收。

| 合规项 | 要求 |
|--------|------|
| 文档骨架 | 与模板一致：`# 设计系统文档：[产品名]` → `> UI 模式：…` → `## 1` … `## 6`，节间用 `---` 分隔 |
| §1 | 含 `### 创意北极星：「…」` |
| §2 | 含叙事段 + `### 色板` + `### 语义色` + `### [布局边界规则名]` + `### 表面层级与嵌套`；`### [特殊质感规则名]` 不适用时须保留子节并注明跳过 |
| §3 | 含叙事段 + `### 字号阶梯` + `### 信息层级` + `### 字体实现约束`（不适用时注明跳过） |
| §4 | 含叙事段 + 叠层/阴影/幽灵描边三条 bullet + `### 叠色对照表` |
| §5 | 含引导段 + 模板所列 **10 个** `###` 子节，顺序与标题一致（搜索框/Loading 不适用时在该子节注明跳过，**不得**删除子节） |
| §6 | 含 `### 应当：` 与 `### 禁止：` 列表 |
| 占位替换 | 将模板中 `[…]`、`#______`、`[产品名]` 等占位替换为已确认内容；**不得**把占位符原样留入终稿 |

内容须同时满足以下规则：

- 文首注明 `ui-mode`（`spec-driven` 规范驱动 UI 或 `mockup-driven` 稿驱动 UI）
- 色彩给出四组主色 + 色阶表 + §2 语义色；§3 给出三档字体族与实现约束（受限运行时）；§4 含叠色对照表；§5 须覆盖通用 UI 原语清单
- **§5 范围规则：** 只写通用 UI 原语；禁止页面名、业务字段布局、功能专属复合组件、领域术语、业务状态名
- **语义色写入规则：** error / success / warning / info 须在 §2 定义 Token + HEX；§5 输入错误态引用 `semantic-error`；§5 状态徽章只写组件形态与通用样例，不写业务状态
- **叠色写入规则：** §5 禁止仅写 `primary @ N%` 等简写——复用 ≥2 次的叠色须在 §4 对照表固化并在 §5 引用 Token 名；单次不复用的叠色须直接写 HEX
- **mockup-driven 分工：** PNG 管页面视觉与功能组件布局；DESIGN 管 Token、通用 UI 原语与实现边界（含字体 fallback、叠色对照表）。不得因「有 PNG」而省略实现约束，也不得在 DESIGN 重复 PNG 已覆盖的页面规格
- **字体实现规则：** 受限运行时（小程序 / RN / Flutter / 原生 APP）须在 §3 写明加载策略与 fallback 栈；稿面字体与实现字体不一致时须分别列出

**写入前品牌板自检（Agent 内部执行，缺项则回到对应拷问项补问，不得写入）：**

**A. 模板结构（对照 DESIGN-TEMPLATE.md「模板」章节）**

| 自检项 | 通过 |
|--------|------|
| 章节顺序、标题层级、`---` 分隔与模板一致 | ☐ |
| §2–§5 各 `###` 子节齐全，无不适用项被整节删除 | ☐ |
| 无模板外新增章节或子节 | ☐ |
| 占位符均已替换为已确认内容 | ☐ |

**B. 品牌板内容**

| 自检项 | 通过 |
|--------|------|
| 按钮四变体 + 反色按钮均有 Token 与交互态 | ☐ |
| 输入框默认 / 聚焦 / 错误态已定义 | ☐ |
| 输入错误态引用 §2 `semantic-error`，非临时 HEX | ☐ |
| 卡片容器样式已定义（无业务字段布局） | ☐ |
