# ADR 格式

ADR 位于 `docs/adr/`，使用顺序编号：`0001-短标识.md`、`0002-短标识.md` 等（如 `0001-event-sourced-orders.md`）。

惰性创建 `docs/adr/` 目录—仅在需要首个 ADR 时创建。

> **约束：所有 ADR 的标题、正文与模板中的内容必须全部用中文书写，必要的英文术语可保留，不允许中英混杂。**

## 模板

```md
# {决策的简短标题}

{1-3 句：背景是什么、我们决定了什么、为什么。}
```

就是这样。一个 ADR 可以只有一个段落。其价值在于记录**做了什么**决策以及**为什么** — 而不是为了填满各个章节。

## 可选章节

仅在确实能增加价值时才包含这些内容。大多数 ADR 并不需要它们。

- **Status** 前置元数据（`proposed | accepted | deprecated | superseded by ADR-NNNN`）— 当决策被重新审视时很有用
- **Considered Options** — 仅当被否决的备选方案值得记住时才包含
- **Consequences** — 仅当需要指出非显而易见的后续影响时才包含

## 编号

扫描 `docs/adr/` 中最高现有编号并加1。

## 何时提议 ADR

以下三者必须均为真：

1. **难以逆转** — 以后改变想法的成本很高
2. **没有上下文会让人困惑** — 未来的读者看到代码会纳闷：“他们到底为什么这样做？”
3. **是真正的权衡结果** — 存在真正的备选方案，并且你基于特定原因选择了其中一个

如果某个决策容易逆转，就跳过它 —— 反正你以后也会把它改回去。如果它不令人意外，就不会有人好奇为什么这么做。如果根本不存在真正的备选方案，那就没什么可记录的 —— 无非就是“我们做了显而易见的事情”。

### 什么算合格

- **架构形态。** “我们使用 monorepo。”“写模型是事件溯源的，读模型投影到 Postgres。”
- **上下文之间的集成模式。** “订单上下文和计费上下文通过领域事件通信，而不是同步 HTTP。”
- **存在锁定效应的技术选型。** 数据库、消息总线、认证提供方、部署目标。不是每个库都需要 — 只是那些换掉需要花一个季度的。
- **边界与范围决策。** “客户数据由客户上下文拥有；其他上下文仅通过 ID 引用它。”明确说不的和说是一样有价值的。
- **与显而易见路径的刻意偏离。** “我们使用手写 SQL 而不是 ORM，因为 X。”任何有理性的人会默认相反选择的场景。这些能阻止下一位工程师“修复”某个本就有意为之的东西。
- **代码中不可见的约束。** “因为合规要求，我们不能用 AWS。”“由于合作方 API 合同，响应时间必须在 200ms 以内。”
- **被否决的备选方案。** 如果你考虑过 GraphQL 但出于微妙的原因选择了 REST，记录下来 —— 否则六个月内会有人再次提议 GraphQL。
