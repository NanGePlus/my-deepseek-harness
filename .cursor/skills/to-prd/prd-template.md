# PRD 模板

> 本文件为 [to-prd](./SKILL.md) skill 的结构模板。Agent 编写 PRD 时**须通读并按此结构**输出；流程与确认规则见 `SKILL.md`。

## 问题陈述

从用户视角出发，描述用户当前面临的问题。

## 解决方案

从用户视角出发，描述问题的解决方案。

## 用户故事

一个长篇幅的、带编号的用户故事列表。每个用户故事应采用以下格式：

US-1：作为 ，我想要 ，以便

US-1: 作为在线购物平台用户，我想要随时查看我的订单状态，以便及时了解商品物流信息。

这个用户故事列表应该极其详尽，覆盖该功能的所有方面。若存在多端（如 Web、APP、小程序、H5 等），请先按端分组依次列出用户故事。

**编号约定**：**PRD 内所有端的用户故事序号必须严格采用 `US-n` 格式引用（如 `US-1`、`US-1~US-3`、`US-3, US-4`），且在所有端内唯一递增。不可在每个端内分别重新编号。** **禁止**用 `#n` 表示故事序号——GitHub Issue 会将 `#n` 自动链接为仓库 Issue，与 PRD 内序号混淆。

## UI 与设计要求

当计划含**可视化页面**时包含此章节；**headless**（纯 API / CLI / 库、无可视化 UI）时省略。

**UI 模式**：

**spec-driven 与 mockup-driven 共用同一套 UI 流程**（见 `SKILL.md` § 流程 step 3）：先定各端 `app-shell` → 按顺序写每页 **UI 设计描述**（含各状态变体）→ 产出页面清单与映射表 → 用户确认。**唯一差异**：mockup-driven 额外须每页 1 张**默认态设计稿**；spec-driven **不要求设计稿**。**两模式均不要求、不规划变体设计稿**（空态 / 错误态等一律写入 UI 设计描述）。

**术语**：

- **默认态设计稿** — mockup-driven 模式下每页须产出的页面设计图，**文件格式为 PNG**（路径 `{platform-id}-{page-id}.png`）。PRD 正文中统称「默认态设计稿」。
- **唯一权威来源（SSOT，Single Source of Truth）** — 某类信息只认一处为准，他处引用、不重复定义。PRD 与自检优先用中文「唯一权威来源」；必要时括号标注 SSOT。
  - **spec-driven** — **UI 设计描述**为编码的唯一权威来源
  - **mockup-driven** — **默认态设计稿**为稿面对齐的唯一权威来源；**UI 设计描述**（含变体段）与 spec-driven 同标准，作为设计稿绘制说明与实现补充，**不**替代设计稿作为稿面对齐依据


| 模式                | 品牌视觉（共用）       | 唯一权威来源（SSOT）          | **UI 设计描述**（PRD 必填）                  | PRD 中禁止                               |
| ----------------- | -------------- | --------------------- | ------------------------------------ | ------------------------------------- |
| **headless**      | 省略整章           | —                     | —                                    | —                                     |
| **spec-driven**   | 引用 `DESIGN.md` | **UI 设计描述**（本 PRD 文字） | 与 mockup-driven **同标准、同流程**；直接指导编码   | 要求设计稿；在 PRD 重写 Token                  |
| **mockup-driven** | 引用 `DESIGN.md` | **默认态设计稿**（每页 1 张）    | 与 spec-driven **同标准、同流程**；状态变体仅写在描述中 | 变体设计稿；在 PRD 重写 Token；跳过设计稿；把描述当作已交付稿面 |


**判定 UI 模式**：优先读 `docs/design/DESIGN.md` 文首 `> UI 模式：…`；若无该文件，沿用 `/grill-with-docs` 会话中已确认的模式。

**文档分工**（勿越界重复）：

- 领域术语与业务规则 → `CONTEXT.md`（PRD 只用其词汇，不重写规则全文）
- 架构 / 技术栈 → `docs/adr/`（PRD 只摘要与本功能相关的结论）
- 品牌视觉（色板、字体、通用 UI 原语、宜忌）→ `docs/design/DESIGN.md`（**禁止**在 PRD 中重写 Token 规格）
- **功能页面规格** → 两种模式均写在本 PRD **UI 设计描述**（同流程、同标准，**含各状态变体**）；**spec-driven** 以描述为编码唯一权威来源；**mockup-driven** 以默认态设计稿为稿面对齐唯一权威来源，描述（含变体段）为设计稿绘制与实现说明


### UI 页面拆解

**页面标识术语**（全文统一，勿混用）：

| 术语 | 含义 | 示例 |
| --- | --- | --- |
| **`page-id`** | kebab-case **机器标识**；用于路由、页面清单条目键、映射表、`references/{platform-id}-{page-id}.png`、Issue **PRD 绑定** | `app-shell`、`home-stores`、`booking-store` |
| **页面标题** | **人类可读**短名，便于 PRD 阅读与顶栏标题示例；**不等于** `page-id` | 「选门店」「预约列表」 |

清单条目标题推荐写为 **`{page-id}`（{页面标题}）**，例如 `home-stores（选门店）`。下游 skill（`/to-issues`、`/triage`、`/tdd`）只认 **`page-id`**，不认页面标题。

**「UI 页」定义** — 下列之一，且满足「该页主路径可被完整描述或交付」：

- 一个独立路由 / 小程序 `page` / App 全屏 Screen
- 一个主导航单元（底栏 Tab、侧栏一级菜单项）对应的常驻主屏
- 一个完整的主任务屏（用户在此完成一项清晰任务的主路径）

**模式下的「可覆盖」含义**（描述标准两种模式相同）：

- **共用** — 该页 **UI 设计描述** 写清布局、字段、主路径交互、各状态与变体；须先有所属端的 `app-shell`
- **spec-driven** — 上述描述即视为可覆盖，可直接进入实现
- **mockup-driven** — 上述描述须足够 AI 绘制默认态设计稿；且每页 1 张**默认态设计稿**覆盖主路径（**仅默认态**，无变体设计稿）

**可算独立 UI 页**（须在页面清单中**单独列出，并标注理由**。不遗漏，不滥拆。定义与判定详见下）：

**判定标准**：（同时满足下列之一，且主路径可独立交付，适合被用户独立感知、验收、测试）
- 一个独立的可路由页面（如 Web Route、小程序 Page、App Screen），即**拥有独立 URL/路由/入口**，非嵌套子元素
- 直接受主导航（底栏 Tab、侧栏菜单等）控制的主屏，高频直接访问
- 一个**完整主用户任务流**承载页（如完整任务填写、审核、结果展示等能闭环的流程页）
- **全屏**的 Modal / Dialog / 流程性 Overlay，且该流程与承载主页**解耦，可独立验收**（如登录弹窗、独立业务表单、授权确认）
- 多步向导流程中，**每一步**若为独立路由/页面则各自单列；如同一页面内流转（非独立路由），在此页明确步骤
- **各端整体框架页**（`app-shell`，详见「整体框架页」章节）：每个 `platform-id` 必有且仅有 1 项，**必须在各端页面清单首位**；壳层可无直接对应用户故事，**不计入「孤立页面」校验**
- 业务明确要求**页面级状态隔离**时（如为实现权限控制、显式子流程跳转、需独立验收测试环境），经需求方/产品认定合理者，也可单列为页，并在 PRD 说明理由

**不应单独算 UI 页的常见情形**（务必合并至所属主页面或主流程，不单独出现在页面清单中）：
- Toast、Snackbar、弹出确认框、结果提示、临时悬浮提示（非流程主干、无主导航入口）
- 抽屉 / 侧滑面板 / Popover / Dropdown，仅作主页面交互流转的功能块，无独立闭环任务主路径
- 非全屏 Loading、骨架屏、局部错误/空态等 UI 状态变体（应在所属页「UI 设计描述」的状态变体段说明，**禁止单列页面**）
- Tab 下内容、侧栏切换等**同层级内容**（区块划分，不是页面级边界）

**注意**：判断存在疑义时，务必与产品/需求方核对归属与验收标准，保证每一独立 UI 页均有明确定义、交付边界、可独立测试和用户感知价值。

**拆解规则**（两种模式共用）：

1. **任务闭环** — 一页完成一个用户任务的主路径；强耦合 UI（列表 + 行内操作 + 分页 + 筛选栏）合在同一页
2. **导航对齐** — 页面边界与产品导航结构一致（Tab、菜单、路由表）
3. **多端对齐** — 同一业务能力在各端分别列页；某端无此功能则标 `N/A` 并写原因
4. **复用 DESIGN** — 页面须基于 `DESIGN.md` 全文已有 Token 与原语组合（§2–§6）；若 §5 缺 pattern，标注「待扩展 DESIGN §5」
5. **先壳后页** — 每个 `platform-id` **必须先**产出 `app-shell`**（整体框架页）** 的 UI 设计描述，**再**写该端功能页；mockup-driven 额外须 `app-shell` 默认态设计稿；功能页不得从零发明导航壳层

**模式追加规则**（在共用流程之上，仅下列差异）：

- **共用** — **一页一描述**：每 UI 页须有独立、足够详细的 **UI 设计描述**；不得用「见某页」含糊带过主路径；须先 `app-shell` 后功能页
- **spec-driven** — **无设计稿**；UI 设计描述即唯一权威来源
- **mockup-driven** — **额外**一页一稿：每 UI 页 1 张**默认态设计稿**；**禁止**变体设计稿（`-empty`、`-error` 等后缀稿）；**禁止**跳过描述直接列设计稿路径

**反模式（须避免）**：


| 过粗                        | 过碎                         |
| ------------------------- | -------------------------- |
| 一页塞入列表 + 详情 + 编辑多个主任务     | 把加载 / 空 / 错误态各拆成独立「页」      |
| 一个「管理后台」覆盖所有模块            | 列表与行内即可完成操作拆成两页            |
| mockup：单稿硬塞多步表单且无步骤标注     | 每个 Toast / 确认框各算一页         |
| 有 UI 设计描述留空或仅一句（两模式均禁）    | 全站共用一个模糊页面描述               |
| spec：要求设计稿 / mockup：跳过设计稿 | 规划变体设计稿（两模式均禁）             |
| 跳过框架页直接写功能页               | 每个端重复写一遍完整顶栏 / 侧栏 / Tab 规格 |


### 整体框架页（`app-shell`）

**定义**：每个 `platform-id` 的**应用级布局壳层**——固定或半固定的导航 chrome + 内容区占位，**不**承载具体业务主任务。功能页在此壳层的内容区内切换。

**为何必须先写**：整体框架决定各功能页共享的顶栏 / 底栏 / 侧栏形态、内容区边距与背景；先定壳再定页，避免功能页各自发明导航、稿面风格漂移。

**命名与清单位置**：

- **`page-id`** 固定为 `app-shell`（多端并存时在页面清单中按端分组，每端第一条）
- mockup-driven **默认态设计稿**（每页 1 张，无变体后缀，文件 `.png`）：`docs/design/references/{platform-id}-{page-id}.png`（**spec-driven 不需要**）
- **须出现在页面清单中**，排在**该端所有功能页之前**

`app-shell` **UI 设计描述须覆盖**（不写具体业务字段）：

1. **viewport 分区** — 顶栏 / 侧栏 / 底栏 Tab / 内容区 / 安全区（小程序）各占高度或宽度；背景 `surface-`* 分区
2. **导航 chrome** — 菜单项 / Tab 项文案与顺序、图标尺寸、选中 / 未选中态（引用 §5 导航 Token）；侧栏宽、折叠态（若有）
3. **顶栏公共元素** — 标题区、门店名 / 用户菜单 / 全局搜索等**跨页复用**元素的位置（即使某页隐藏，也须在壳层说明「何页显示 / 隐藏」规则）
4. **内容区约定** — 内容区背景、默认页边距、是否允许全宽 / 固定底栏 CTA 占位
5. **壳层变体** — 如：登录页**无壳**、预约流**隐藏底栏 Tab**、选店页**无侧栏**——在壳层描述中列出「脱离壳层 / 缩减 chrome」的页面名单，供功能页引用

**功能页如何引用壳层**：

- UI 设计描述**首句**须写明壳层关系，例如：「继承 `wechat-mini` **app-shell**，底栏 Tab 选中『首页』；本页仅描述内容区。」或「**脱离 app-shell**（无顶栏 / 无底栏），全屏独立任务页。」
- **禁止**在功能页重复描述已在 `app-shell` 定稿的顶栏 / 侧栏 / Tab 全规格；只写相对壳层的**增减**（如隐藏 Tab、增加步骤条、固定底栏 CTA）

**与用户故事映射**：`app-shell` 可不对应单一故事；映射表该行故事列可写 `—（壳层）` 或列出支撑的导航类故事编号（如 `US-16~US-17`）。

**特殊情况说明与范例**

以下页面虽与框架壳层相关，但不算作 `app-shell`，需在「壳层变体」中登记说明：

- **脱离壳层页面**：如登录、授权等**全屏无 chrome**的页面，需要在 `app-shell` 的「壳层变体」中明确定义为“脱离壳层页面”。
- **局部chrome缩减页面**：如全屏 Modal 或独立向导页面，并不会作为 `app-shell`，但功能页描述中应写明此类页面相较标准壳层的 chrome 减少或变化规则。

**app-shell 设计范例（以微信小程序为例）：**

- **page-id**：`app-shell`
- **主职责**：定义整个小程序的全局导航壳层，作为所有功能页的布局和导航基础，不承载具体业务任务。
- **支撑用户故事**：—（壳层本身支撑 US-16~US-17 Tab 导航等全局导航/布局相关主线）
- **默认态设计稿（仅 mockup-driven）**：`wechat-mini-app-shell.png`（待提供；路径为 `docs/design/references/wechat-mini-app-shell.png`）
- **DESIGN 复用**：顶栏采用 DESIGN.md §5 导航栏 token，底栏 Tab 同样引用 DESIGN.md §5 相关规范。
- **UI 设计描述**：
  1. **viewport 分区**：分为三部分——
     - 顶栏，44px 高度 + 状态栏，背景为 `surface-base`，标题居中，字体 `text-headline-lg`，内容可被子页注入；
     - 内容区，flex 填充剩余高度，背景 `surface-base`，默认左右边距 16px；
     - 底栏 Tab，50px 高度 + 安全区，背景 `surface-card`，上方有 `neutral-100` 分隔线，三大导航 Tab「首页 / 我的预约 / 我的宠物」，图标 24px，标签 10px，未选中态色 `neutral-400`，选中态色 `primary-500`。
  2. **壳层变体**：
     - 预约流程相关子页（如 `booking-`*）需**隐藏底栏 Tab**、顶栏展示返回按钮；
     - 登录 / 手机号授权页（如 `auth-phone`）**完全脱离壳层**，无顶栏和底栏；
     - 其余需要调整 chrome 的页面均需在此处列明（如全屏 Modal/向导型页面等）。
- **功能页引用规范**：功能页的 UI 设计描述开头须说明其与 `app-shell` 的继承、变体或脱离关系，如“继承 `wechat-mini` app-shell，仅描述内容区”，“脱离 app-shell，独立全屏页”等。严禁在功能页重复描述壳层已确定的顶栏、底栏、Tab 等规格，仅说明与壳层的“增”“减”部分。


### 用户故事 ↔ 页面映射

**必填。** 表格须覆盖所有带 UI 的用户故事；每条 UI 故事至少对应一页；每页至少支撑一条主路径故事。

**术语**：

- **孤立故事** — 涉及 UI 的用户故事未映射到任何页面
- **孤立页面** — 页面未支撑任何用户故事（`app-shell` 除外）


| 用户故事编号 | 端       | page-id       | 该页承担的故事范围     | UI 设计描述要点             | 默认态设计稿（仅 mockup-driven）          |
| ------ | ------- | --------- | ------------- | --------------------- | -------------------------------- |
| —      | 微信小程序   | app-shell | —（壳层）         | 顶栏 / 底栏 Tab / 内容区…    | `…/wechat-mini-app-shell.png`    |
| US-3, US-4 | Web 管理端 | today-bookings | US-3 浏览、US-4 搜索筛选 | 表格列、筛选栏、继承 app-shell… | `…/web-admin-today-bookings.png` |


- **spec-driven**：「默认态设计稿」列整列写 `N/A` 或省略该列
- **mockup-driven**：两列均须填写；UI 设计描述要点与页面清单中的完整描述一致或为其摘要

映射完成后自检（**两模式共用前 6 项**）：

- [ ] 无**孤立故事**（有 UI 的用户故事均已映射到页面，或在某页 UI 设计描述变体段中覆盖）
- [ ] 无**孤立页面**（每页至少支撑一条主路径故事；`app-shell` **除外**）
- [ ] **每个** `platform-id` **均有且仅有一个** `app-shell`，且排在该端功能页**之前**
- [ ] `app-shell` **UI 设计描述**已写壳层分区 / 导航 / 内容区约定 / 壳层变体；**先于**该端功能页完成
- [ ] 功能页 UI 设计描述**首句**已声明继承或脱离 `app-shell`，未重复壳层全规格
- [ ] 页面清单中**每页 UI 设计描述**非空且足够详细（与模式无关）
- [ ] **spec-driven**：全文**无**设计稿路径要求
- [ ] **mockup-driven**（额外）：每页 1 张默认态设计稿计划；**无**变体设计稿；描述（含变体段）足够 AI 绘制设计稿并与实现对齐


### 状态策略

**必填**（非 headless PRD）。下游 `/to-issues` UI issue「PRD 必读」第 2 项、`/tdd` 预检均按 **`### 状态策略`** 打开本章节 — **禁止**省略或拆散到各页描述中而不写本章。

**「页」与「态」分离** — 加载中 / 空 / 错误 / 禁用 / 上传是**同一页的状态变体**，默认不是独立 UI 页。**两模式均不要求变体设计稿**；各态一律在 **UI 设计描述** 中写清，或注明「复用 DESIGN §5 ___」。


| 状态           | 处理方式（两模式相同）                                     |
| ------------ | ----------------------------------------------- |
| 加载中          | UI 设计描述逐页写明，或「复用 DESIGN §5 Loading / 骨架屏」       |
| 空状态          | 描述末尾 **变体段**（如「空状态变体：…」），或「复用 §5 empty-state-*」 |
| 错误 / 禁用 / 上传 | 描述末尾 **变体段**，或「复用 §5 输入错误态 / …」                 |
| 搜索展开、表单抽屉等   | 同上，写变体段；**不**单独出设计稿                             |


**mockup-driven 补充**：默认态设计稿 **只画主路径默认态**；空态 / 错误态等由 UI 设计描述 + `DESIGN.md` §5 指导实现，**不**追加 `-empty`、`-error` 等变体稿。


### 页面清单

每页除主任务、覆盖故事、DESIGN 复用外，**必须**附 **UI 设计描述**——用自然语言详细说明该页应如何画 UI / 如何实现，**无需**重复 `DESIGN.md` 中的 Token 数值（只引用 Token / 组件名）。**spec-driven 与 mockup-driven 使用同一描述标准与清单格式**；mockup-driven **额外**增加默认态设计稿字段。

**清单顺序（强制）**：按 `platform-id` 分组；**每组第一条必须是该端的** `app-shell`，其后才是该端功能页（按主路径 / 导航顺序排列）。**每个功能页必须单独成条，不允许两张页面合并到一个清单条目中，一个功能页对应一条清单记录，禁止将多个页面描述或内容合并为一页。**

**每页条目格式**（两模式共用；mockup-driven 多一行默认态设计稿）：

- **端 / 运行环境**
- **page-id** — kebab-case 标识；与映射表、`references/`、Issue 绑定一致
- **页面标题** — 人类可读短名（如「选门店」）
- **主任务** — 用户在此完成什么
- **覆盖的用户故事**（`US-n` 格式，如 `US-3` 或 `US-1~US-3`）
- **默认态设计稿**（**仅 mockup-driven**）— 每页 1 张，路径 `{platform-id}-{page-id}.png` 或「待提供」；**不含**变体后缀稿
- **DESIGN 复用** — 本页用到的 §5 原语；若有「待扩展 DESIGN §5」须写明
- **UI 设计描述** — **必填**；见下方写作要求


#### UI 设计描述 — 写作要求

**撰写顺序**：先完成该端 `app-shell`，再写功能页。

一段连续自然语言（可含 **变体段**），须足够详细，使 AI **无需猜测** 即可编码（spec-driven）或绘制默认态设计稿（mockup-driven）。**两模式描述深度与结构要求完全相同**。

**功能页**描述首句须声明壳层关系（继承 / 脱离 `app-shell` + 选中 Tab 或菜单项）；`app-shell` 描述壳层本身，不写业务字段。

按优先级覆盖：

1. **整体框架** — `app-shell`：viewport 分区与导航 chrome 全规格。**功能页**：相对壳层的内容区布局；顶栏 / 底栏 / 侧栏仅写**相对壳层的增减**（如隐藏 Tab、增加返回、固定底栏 CTA）
2. **区块与阅读顺序** — 自上而下 / 左右栏各有什么；区块间距；哪些用 `card-default` / `card-inset` / `card-elevated` 包裹，哪些直接铺在 `surface-base` 上
3. **信息层级** — 主标题 / 正文 / 标签各用什么 typography 角色 + 颜色 Token（如 `text-headline-lg` + `neutral-900`）；关键业务文案示例（按钮文字、placeholder、空状态主文案）
4. **组件规格** — 列表行高、头像尺寸与是否溢出卡片、按钮类型与文案、输入字段顺序、表格列、搜索框宽度、徽章变体等业务专属布局
5. **交互与状态** — 选中 / 悬停 / 禁用 / 提交中 spinner 的表现；单选圆环、时段格选中等模式-specific 态
6. **变体差异** — 默认态（及 mockup-driven 默认态设计稿）覆盖主路径；空态 / 错误态 / 禁用态 / 上传中等在描述末尾用 **变体段**（如「空状态变体：…」「错误变体：…」）说明与默认态差异；或「复用 DESIGN §5 ___」。**禁止**为变体单独规划设计稿
7. **宜忌对齐** — 符合 `DESIGN.md` §6（如一步一事底栏 CTA、宠物头像可略溢出、禁止实线区块分隔等）

**禁止**：复制粘贴 `DESIGN.md` 色板 HEX / 字号像素表；用模糊短语代替布局；mockup-driven 下写「见设计稿」而描述留空；spec-driven 下要求设计稿；**两模式均禁止变体设计稿**（`-empty`、`-error`、`-form` 等后缀稿）；正文不写「出稿 PNG」。

**篇幅参考**：小程序单步页通常 150–250 字；管理端列表 / 配置页 200–350 字；含多区块或变体时可更长。

**设计范例（以微信小程序为例）：**

#### `app-shell`（微信小程序整体框架）

- **主任务**：定义全局导航壳层
- **覆盖的用户故事**：—（壳层）
- **默认态设计稿**（仅 mockup-driven）：`wechat-mini-app-shell.png`（待提供）
- **DESIGN 复用**：小程序顶栏 §5、底栏 Tab §5
- **UI 设计描述**：整体框架页，定义微信小程序的全局 viewport 分区。顶栏含品牌 Logo、页面标题与系统状态区，默认置顶不滚动；底栏为固定 Tab 栏，按主流程区分页面入口（如「首页」「预约」「我的」），激活项高亮、其余为常规色。各区块间统一留白，遵循 §5 通用原语，不设侧栏。框架布局及交互与 DESIGN.md §5 导航和区块定义保持一致，禁用明显分割线。字体与 Token 引用 DESIGN.md §3、§5，并注明字体受限适配。交互态包括 Tab 切换、底栏被动收起（表单输入交互时）。无变体段。

#### `booking-store`（选门店）

- **主任务**：选定 1 家门店
- **覆盖的用户故事**：US-3
